# Inkling-2-Mini tensor parallelism

Use one rank per GPU. Keep the residual stream, message controllers, router and post-projection convolution state replicated. Shard attention by complete GQA groups, each routed expert by its intermediate channels, and the target head by vocabulary rows. Each of the 48 visits needs two rank exchanges on this layout. One publishes the attention write before the MLP read. The other publishes the MLP write before the next residual read. The greedy head needs one additional candidate exchange per forward.

On Dual-Spark, use mapped host memory, one prestarted CPU proxy per rank and both ConnectX-7 rails. The model records stream-ordered collectives into its existing graph schedule. A future B200 backend can use NVLink multicast and keep the same schedule and rank layout. At the measured single-Spark baseline of about 56 token/s, the working TP=2 projection is **86–97 token/s, 1.54–1.72×**, for plain greedy decode with FP8 dense weights and FP8 full KV. This assumes 80–90% of baseline time scales with the sharded work and 5.5–9 µs per BF16 exchange. Neither assumption has been measured on a TP run.

For each KV channel the sliding kernel adds the current input to its four-tap convolution and scales by `1/sqrt(5)`. Full attention adds the per-head dynamic tap to each channel's static tap by lag, adds the current input and scales by `1/3`. Both round to BF16, clip K per head, RMS-normalize V per head without a learned scale, and store in the selected cache dtype. Q and relative vectors get learned scales and per-head clipping, with full attention applying its length-dependent scale. The causal, position-masked softmax uses the local Q and KV group, relative scores and attention sink. The per-channel output gate consumes the BF16-rounded attended value. No cross-rank statistic is needed in these steps.

The first exchange sits between the `wo` dot and `conv_attn`. Split `dense::proj_conv` at that seam. The legacy epilogue rounds the dot to BF16, convolves the rounded input with the three prior values and updates FP32 convolution state. A BF16 wire path casts each FP32 partial, sums in FP32 and rounds the result to BF16. This adds a rounding step and can change the dot's reduction order. An FP32 wire path sums partials first and rounds once. Keep the post-conv FP32 write for residual mix and ablation. ### Residual and cross-pass messages

`B0` comes from the replicated BF16 `[201024,H]` embedding and FP32 embedding norm. Tokens, position and tap indexing are replicated. Attention reads the completed blocks selected by `Buffers::blocks`, the current partial residual, and the preceding MLP write. At a six-layer block boundary, the MLP read includes the completed hidden as a block and uses no partial base. Otherwise it adds the current attention write to that base. The ablation direction, detector and coefficients apply to the corresponding global write inside the consuming mix. Its dot products, thresholds and nonlinearities require full-hidden values. Replicate the parameters and compute the ablation after the exchange. The final read mixes `B0, B1, B2[2], E[2]`, the last partial and the last MLP write, applies the final query and norm, and publishes the fourth tap and head input.

`B1` receives the hidden entering layer 6 on pass 0 and is reused as the starting residual for passes 1 and 2. `B2[p]` saves the hidden entering layer 12 of pass `p`. At layer 6 of each later pass the previous pass's last MLP write completes `E[p-1]` inside the message mix. For the rest of that pass the four message queries read `B2[p-1]` and `E[p-1]`. The write is consumed once in that previous-pass completion. Layer 18 stores `E[2]` and proceeds with the final six layers. For message visits, the attention-side mix and message mix can remain paired. `message_gates` applies three Q/K/V controllers before attention and one MLP controller after the attention write. The residual and message reads use per-source RMS normalization and query-dot softmax weighting. Each gate projects the concatenation of normalized hidden and message to 64 BF16 lanes, computes forget and gain with tanh, forms `(1-forget)*hidden + gain*message`, and RMS-normalizes and casts the resulting row. The gated BF16 outputs feed the local projection and the replicated router.

Replication adds **zero** cross-pass collectives. Sharding just the gate output channels with the current full-hidden consumers adds one batched Q/K/V gather and one MLP gather at each of the 24 message visits, for **48 additional collective stages**. An implementation that normalizes gate outputs while they are still sharded also needs global RMS statistics. Reconstructing the pre-norm vector at the gather permits the full-width norm to stay local. ### Routed experts and the precision boundary

Replicate `router[128,H]` (FP32 copy), `router_bf16[128,H]`, `router_bias[128]`, and the router top-eight computation. `idx[M,8]` and weights `wts[M,8]` must agree across ranks, including the tie and ordering rule. Every rank processes the same selected experts and multiplies a slice of each expert. There are no shared experts or input routes to exchange.

For a shard owning logical intermediate channels `[j0,j0+J)`, select W13 rows `[2*j0,2*(j0+J))` of each expert. Gate and up rows are **interleaved** by channel. W13 keeps all `H` input columns and corresponding block scale rows. Slice W2 columns in every expert and every output row, using the matching scale columns. Copy the two NVFP4 outer factors for each expert unchanged on every rank. They are global per-expert FP32 `amax / outer_scale_denominator`.

The TP=8 MXFP8 split has 11.1% more channels on the larger ranks than a hypothetical balanced width of 144 and a 1.25× heavy-to-light ratio for those four layers. The other 44 visits keep equal logical width. A separate optimized half-block loader could balance later, but the plan uses whole blocks. In all cases zero or mask tail loads before MMA. `I/128` integer truncation silently drops channels, including at TP=2.

**The MoE write has two supported precision modes.**

1. **Fast BF16.** Keep W13's legacy rounding of gate and up before softcapped SwiGLU, and BF16 activations. W2 produces FP32 partial dots. Take the routing-weighted sum of local partials in FP32 in router slot order and exchange one BF16 `[M,H]` buffer per rank. Sum in FP32, round once for the shared convolution input, then run `conv_mlp`. This rearranges the router-weighted sum around the W2 rank reduction and omits the baseline's BF16 rounding of *each complete expert dot*. Measure its error separately from BF16 communication error.
2. **Ordered expert accumulation.** Gather FP32 W2 partials by router slot (or use an FP32 vector reduction), add corresponding rank partials, round each complete expert dot to BF16, multiply by the same router weight in the original slot order, round the sum to BF16, then convolve. This preserves the order of expert and routing roundings and narrows the difference to dot-product grouping. At TP=2 a direct exchange sends `8*M*H*4 = 73,728*M` bytes per rank for that visit, 16× the fast-path MLP payload. An ordered rank-gather is suitable for diagnosis and as a precision fallback. A cheaper FP32 hidden reduction can isolate the wire rounding but still rearranges expert rounding.

The shipped mode is chosen by parity on the matched TP=1 baseline. Exact legacy output is a separate oracle. For example, the current W2 sums nine warp partials in order. At TP=2 an optimized kernel sums differently and the 576 boundary splits a 128-channel warp group. A debugging reconstruction gathers W13 activations in global channel order, reassembles W2 with original codes/scales and runs the unchanged full-width dot and epilogue. The attention oracle similarly reassembles all `attn_out` heads before the unchanged `wo` and conv. Use both to separate layout or history bugs from expected arithmetic differences.

**Expert parallel comparison.** With this already replicated router and full input, static EP can locally mask unowned experts, run full-width W13/W2 and reduce the routed result. It needs one MLP collective per visit, like TP. There is no reason to dispatch activations by all-to-all in this single-stream design. EP preserves the full-width W2 dot and per-expert rounding locally. Grouping weighted sums by owning rank still changes the combine order unless it exchanges results in slot order. EP also needs an expert-ID remap, local masks, an empty-rank path and tests of imbalance. With two equal expert pools and uniformly chosen distinct top eight, the slower rank gets 5.06 experts on average at `M=1` and at least six on 27.3% of visits. Actual routing can be more skewed. For iid token routes the expected unique experts across the call at `M=1/4/8/16` are 8.0/29.1/51.6/82.4. Repeated experts are loaded once per call where kernels reuse them. Rank skew can persist even at larger widths. TP gives equal expert work at P=2/4 and reuses the existing routing, dedup and weighted-combine contracts with narrower dots. Use TP for M1–M4. If comparing EP on B200, use real routing histograms and include the critical rank's compute time. ## 2. Head, speculation and collective count

**Vocabulary.** Shard just the unpadded unembedding, with global offsets `[0,100029)` and `[100029,200058)` at TP=2. The two ranks each store 100,029 rows. At TP=4 assign 50,015 rows to the first two ranks and 50,014 to the last two. At TP=8 assign 25,008 to the first two and 25,007 to the rest. Row-local softcap is unchanged. For greedy, exchange one `{float logit, int32 global_id}` per row (8M bytes transmitted per rank at TP=2) and pick the largest logit, breaking ties to the lower global token ID. This matches `head::argmax`. Decode and greedy spec can use the same result on all ranks. Forced replay consumes the same forced sequence on all ranks and can still run greedy scoring for comparable timings.

**Sampling.** The union of each rank's local top-k is enough to recover the exact global top-k for bounded `k`. Use the same global ID ordering, temperature, top-p filter, renormalization and RNG draws on that merged candidate set. Payload is 8Mk bytes per rank at TP=2. An unbounded top-p or full softmax can include any vocabulary row. The M3/M4 correctness path gathers sharded FP32 logits in global row order to rank 0, which runs the existing sampler or verifies against gathered logits and broadcasts decisions. Each TP=2 rank's shard is `400,116*M` bytes. The current sampled accept computes target probabilities from temperature/top-k/top-p, checks `min(1,p(draft)/q(draft))` using DSpark draft statistics and uniforms, then samples the positive residual `max(p-q,0)` at the first rejected row or target p on full acceptance. The kernel's all-zero residual fallback uses p. Shortlist-only target argmax/top-k cannot generally implement this. A distributed sampled fast path can later use exact global cutoffs and normalization, collect proposed-token probabilities, and sample from distributed residual mass. To preserve seeded behavior, retain the current RNG counter/order and use global token IDs in any distributed RNG or tie-break operation. Use the full-logit path as oracle, including the existing fixed-point top-p cutoff. Sources include `spec.cpp:82–115,181–200`, `kernels/head/head.cu:1–14,116–151`, `kernels/draft/accept.cu:24–105`.

**DSpark.** Keep the drafter on rank 0 for the first integration. `mtp.safetensors` on this host is 635,801,416 bytes (606.35 MiB). The current loader materializes 477,106,196 bytes of persistent derived parameters and folded head, before the shortlist, target unembedding, KV and scratch. Two local BF16 rings contribute 8,454,144 KV bytes and the global FP8 ring contributes `2048*min(C,65536)` bytes, plus local ring position tags. All verifier taps already exist at full width on rank 0, so commit needs no tap exchange. The current drafter binds the full target head, uses it to build its folded head and initial shortlist, and sources new context shortlist rows from it. M4 should give the drafter an explicit full-vocab row source and vocabulary size, separate from the verifier's shard. The simplest rank-0 implementation retains the other target shard for the drafter, adding 230,866,932 dense-FP8 bytes or 460,933,632 BF16 bytes on rank 0. A later row provider can build the folded head in chunks and lazily stage just the shortlist and newly observed context rows.

Rank 0 chooses width from confidence, broadcasts seven int32 draft IDs and one int32 width/count as a **32-byte linear verify header**, and then both ranks verify that ordered input with the same anchor and position, already known from the prior decision. It also publishes a compact accept/next/stop record in sampled mode so both ranks roll back and commit the same rows. Greedy acceptance can run on both ranks from identical proposals and globally merged argmax. Rank 0 alone extends the draft KV and shortlist. Use a fixed prefix node before the CUDA graph switch on both ranks or launch the agreed fixed-width graphs; broadcast before evaluating the conditional handle. Drafting is already on the critical path of the next verification, so rank-0 ownership saves memory and redundant GB10 compute but adds one small exchange and leaves rank 1 waiting for proposals. Expect roughly one small-message 5–9 µs class exchange per round, with control and scheduling latency to be measured. Replicated lockstep can remove that proposal exchange, but both ranks then pay the drafter footprint, the additional head row-source footprint, and full draft compute. It also requires identical RNG/shortlist updates and proof both ranks produce the same proposal, width and accept result. A mismatch at a conditional graph would break collective order. Sources include `drafter.cpp:54–175,186–303,440–565`, `drafter.h:46–55`, `spec.cpp:39–72,118–224`.

**Barrier count.** Each visit consumes the complete attention write before router inputs and consumes the complete MLP write before the next attention read, pass-end message or final read. Thus the fast decode and prefill plans issue **96 hidden SUMs per forward/chunk**. The last MoE write feeds the head, and the MLP writes at loop seams complete the message state. Stream-ordered convolution can fuse into the receive/reduction epilogue when numerical and history contracts are preserved. It cannot remove either dependency. The ordered-expert fallback replaces 48 of the SUMs with wider exchanges, keeping the same number of synchronization stages. Collectives can be replaced with gathers and redundant work under a different layout, but two dependent exchanges per visit remain in this design. The greedy head adds one candidate gather per forward, usually **97 collective stages total**. Prefill prompt admission, sampled accept, draft control, and optional image embedding transfer add their own stages. There is one set of 96 per verify call, shared by its M rows.

TP=2 uses `Klocal=512`. Per request there is 83,886,080 bytes of BF16 ring KV across 40 visits (two caches). The eight full visits add `8192*C` bytes for E4M3 or `16384*C` for BF16. The tag array adds 327,680. The two local K/V conv histories add 589,824 in total. The two replicated attention/MLP conv histories add 2,654,208 in total. Here conv history means each visit's persistent three-token state.

## 4. Runtime and transport boundary

The TP runtime owns `TpLayout` (rank, sizes, checkpoint slices and local tensor descriptors), the deterministic visit schedule, input distribution, request ordering and commit/rollback decisions. Its kernel interface takes ordinary device buffers, explicit dimensions and strides, and a CUDA stream. Kernels do local GEMV, grouped attention, experts or state transitions. The transport sees byte spans, scalar type, rank, epoch and stream. It has no knowledge of layer count, hidden size, RoPE, routing or expert format. A single-rank implementation performs copies or aliases and runs the same graph-oriented decoder. A one-device simulated backend supports M2.

```cpp
struct CollectiveSite {
  uint32_t schedule_id;  // fixed across ranks for this graph/phase
  uint32_t op_index;     // fixed within schedule, independent of replay
};

class CommBackend {
 public:
  virtual ~CommBackend() = default;

  // Out-of-capture setup. Env selects rank, world size, local device, rendezvous
  // and transport. Allocate/register graph-stable scratch before recording.
  static std::unique_ptr<CommBackend> init_from_env(const CommPlan& plan);

  virtual void allreduce_bf16(DeviceSpan<const Bf16> src,
                             DeviceSpan<Bf16> dst,
                             CollectiveSite site, cudaStream_t stream) = 0;
  virtual void allgather_small(DeviceBytes src, MutableDeviceBytes rank_order_dst,
                               CollectiveSite site, cudaStream_t stream) = 0;
  virtual void broadcast_tokens(MutableDeviceBytes record, int root,
                                CollectiveSite site, cudaStream_t stream) = 0;

  // Same ordering contract for precision fallback, prefill and validation.
  virtual void allreduce_f32(DeviceSpan<const float> src, DeviceSpan<float> dst,
                            CollectiveSite site, cudaStream_t stream) = 0;
  virtual void gather_rows_to_root(DeviceSpan<const float> local,
                                  MutableDeviceBytes root_dst, const GatherLayout& layout,
                                  int root, CollectiveSite site, cudaStream_t stream) = 0;
};
```

All operations consume device memory and publish rank-ordered or reduced results in stream order, during eager enqueue or graph recording. No capture-time buffers or host sends. Message sizes, padding, destinations and scratch lifetimes are fixed for each recorded shape. `allgather_small` concatenates fixed-size per-rank records, padding and carrying validity counts when needed. `broadcast_tokens` copies an opaque fixed-size device record from root. Validate capacities and support before graph recording. Provide backend health/status outside capture and a device-visible fatal flag. Disable application-visible token publication or checkpoint commit for a failed replay. Initial engine support is one in-flight graph chain per rank and request admission in the same global order. Parallel requests can be added with separate graph-stable slots and explicit scheduling.

The proposed BF16 contract is FP32 accumulation and one BF16 result conversion for already-BF16 input operands. At P=2 this can be tested bit-for-bit with explicit FP32 addition and round-to-nearest-even. P=4/8 hardware or library reduction order may differ. A deterministic rank-ordered implementation remains available for validation, and backend qualification checks rounding and replica equality. The FP32 contract likewise needs a fixed-order mode for reproducibility. Layer arithmetic is separately covered by M2.

### RoceUmaBackend on Dual-Spark

One process and one stream schedule per host. The TCP rendezvous listens on `10.42.101.1:29620` (`rank0`, rank 0); `rank1` is rank 1. Exchange protocol version, rank/layout/checkpoint and graph-plan hashes, run ID, maximum slot capacity and each rail's QP metadata and rkeys. Resolve actual verbs device and RoCEv2 GID for each configured local IP. The launch config advertises these rails:

| Rail | Verbs device | Rank 0 | Rank 1 | Bytes for a BF16 `[M,2304]` SUM |
| --- | --- | --- | --- | ---: |
| 1 | `rocep1s0f1` | 10.42.101.1 | 10.42.101.2 | 2,304 × M |
| 2 | `roceP2p1s0f1` | 10.42.102.1 | 10.42.102.2 | 2,304 × M |

Use one RC QP per rail with separate CQs or explicit CQ ownership and preposted receive WQEs for Write-with-Immediate notifications. Set negotiated MTU/GID and correct source routing on each rail. Allocate host storage with `cudaHostAllocMapped`, obtain its GPU alias and register the underlying host pages with `ibv_reg_mr` in **both** protection domains. Retain the rail-specific lkeys/rkeys. Each slot has distinct disjoint TX and RX bytes and cacheline-aligned single-writer control fields. Register data regions for local/remote write and keep handshake words separate from DMA ranges. For model SUMs, split the flattened contiguous buffer at its midpoint and submit both writes before polling either completion. The two halves can arrive in either order. Use one rail for tiny control messages to minimize doorbells. The two-rail feature is for the P=2 RoCE backend. Future P=4/8 over RoCE would need a separate collective algorithm, while the runtime and `TpLayout` already generalize.

**Replay path for one SUM**

1. GPU pack/produce writes the BF16 partial to the send slot via the mapped alias. Each writer executes a system fence (`__threadfence_system()`), then the CTA joins and a single lane publishes `tx_epoch` via a system-scope release-store. A separately captured publisher can follow a multi-CTA pack as long as all producer stores have the required visibility. Start with one vectorized CTA or a separate publish node. Use an aligned 64-bit monotonically increasing epoch assigned at execution time, so graph replays never reuse a stale ready value.
2. A dedicated, CPU-affined proxy thread busy-polls a host acquire-load of `tx_epoch`. It reserves the destination slot, posts `IBV_WR_RDMA_WRITE_WITH_IMM` on both rails and polls both CQs. An immediate identifies the rail-local slot and a sequence tag. Its 32 bits do not hold the run ID and full epoch. Validate a fixed wire header or an equivalent paired control sequence, plus opcode, byte count, QP, schedule/op index and full epoch. Refresh receive WQEs. Do not block rail 2 behind rail 1's CQ.
3. After observing both matching receive completions and the platform's required host DMA-read ordering, the proxy release-stores the local `peer_ready_epoch`. It also tracks both matching send completions for TX reuse. For the first implementation the proxy can wait for both local send completions before publishing ready, making one slot-release condition explicit. Use the verbs provider's DMA ordering primitives as documented for this host. An IBV send completion alone does not establish that this rank's peer payload has arrived.
4. A stream-ordered GPU receive kernel uses a system-scope acquire-load to wait for the same epoch and then reads the mapped RX halves. It vector-adds local and peer BF16 lanes in FP32, rounds and outputs BF16. It can fuse output conversion or the post-collective epilogue where useful. After all consumers finish reading the slot, publish a local consumed epoch or release the slot through a following ordered node. Limit spinning to a small number of CTAs to avoid consuming resources needed for other work. Epoch/control traffic and a fused pack or sum may be tuned after M1.

The graph contains GPU nodes and fixed addresses. The proxy sits outside capture, calls verbs and host atomics only, and wakes on GPU-produced epochs. There is **zero `cudaStreamSynchronize`** in this path, including replay. End-of-request or benchmark timing may use one graph-completion event. Warm-up, graph construction, buffer registration and teardown are separate.

**Visibility and slot reuse.** CUDA system atomics order the CPU/GPU handoff for naturally aligned mapped words. Use release/acquire load/store with one writer per field, capability-check mapped memory and verify atomic support before using any system-scope RMW. The GPU fence orders its own writes. Incoming RNIC DMA has a separate completion and visibility requirement. The mapped payload is host memory registered with verbs, which NVIDIA documents for Spark. Spark's `cudaMalloc` memory does not support GPUDirect RDMA. Qualify the CQ-to-GPU data visibility on the exact driver, host allocation and cache mode. In M1, repeatedly overwrite the same cache lines with changing payloads, stagger rails and ranks, and detect partial or stale reads. Use a documented mapped-system load mode that observes host-memory DMA, or a host-copy fallback where the proxy copies CQ-completed RX bytes to a separate CPU-written mapped mailbox before release. That fallback uses an extra CPU copy and must pass the same ordering test. If no qualified handoff is available, keep the graph fast path disabled and use a tested stream/host staging path. See [NVIDIA Spark CUDA porting guide](https://docs.nvidia.com/dgx/dgx-spark-porting-guide/latest/porting/cuda.html), [CUDA C++ memory model](https://docs.nvidia.com/cuda/archive/13.4.3/cuda-programming-guide/05-appendices/cuda-cpp-memory-model.html), and [rdma-core memory registration semantics](https://www.man7.org/linux/man-pages/man3/ibv_reg_mr.3.html).

Use separate TX and RX leases. A send completion permits local TX reuse, and the receiver must have consumed the previous epoch before a remote write can overwrite the RX slot. In the bidirectional SUM chain, two rotating slots are sufficient when a rank cannot publish op n until it consumed n−1: its receipt of the peer's n−1 implies the peer previously consumed n−2. Use disjoint graph/request buffers or explicit remote credits when this proof does not apply, especially for consecutive one-way broadcasts. A simple bounded first implementation can reserve a slot per collective site for the entire in-flight replay and retire all slots after a graph-complete handshake. Reserve this option for decode/control sizes. For prefill and wide logit payloads use separate capacity classes and the bounded reuse protocol, with chunking as needed. Pre-arm receives and root/worker readiness in agreed op order. Teardown drains or errors both QPs before deregistering storage.

Use timeouts on the proxy and GPU wait that identify request, graph, op, epoch and rail. On a failed CQ, peer exit, ordering mismatch or timeout, latch terminal status, release bounded GPU waits into a failed replay, and stop both ranks. Drop tentative writes and outputs, then recreate the communicator and restore both ranks from a jointly committed checkpoint. Do not retry a graph on one rank or reuse slots from a failed session. One-rail operation is an explicit mode agreed at initialization; no mid-collective downgrade.

### NvlsBackend on B200

Start with one rank per GPU in one NVLink multicast clique. Query multicast support and team membership, provision symmetric graph-stable windows with NCCL or CUDA multicast VMM, and use fixed offsets across ranks. A stream-ordered producer writes each rank's local unicast window. Establish publish/arrival ordering with a documented device team barrier. The one-shot kernel on each rank reads the same multicast alias with vector `multimem.ld_reduce` and writes the complete result in that rank's local output. The next use of a window waits for all remote readers to retire, using the team barrier or rotating windows with explicit lifetime proof. Aligned BF16x2 multimem with FP32 accumulation is a candidate fast implementation. Validate the actual output conversion and accumulation against the backend contract; use FP32 multimem or an ordered software reduction when needed. Use multicast or graph-compatible NCCL for control and candidate exchanges. Check whether a 2-GPU subset belongs to a multicast-capable team. On plain P2P NVLink or unsupported team/registration, use a qualified NCCL or direct P2P fallback under the same interface. Tune one-shot vs reduce-scatter + all-gather by size, particularly for prefill and FP32 expert parity exchanges. See [CUDA multicast objects](https://docs.nvidia.com/cuda/cuda-driver-api/cuda_driver_api/group__CUDA__MULTICAST.html), [NVIDIA one-shot collective](https://github.com/NVIDIA/nccl/tree/master/contrib/custom_algos/allreduce), [NCCL graph registration](https://docs.nvidia.com/deeplearning/nccl/user-guide/docs/usage/bufferreg.html), and [NCCL CUDA Graph capture](https://docs.nvidia.com/deeplearning/nccl/archives/nccl_2262/user-guide/docs/usage/cudagraph.html).

A backend that cannot record a collective in a conditional body can use rank-agreed width selection followed by launch of pre-instantiated fixed-width graphs. Treat that as a graph-recording capability. The numerical kernel implementation still only sees rank-local tensors and a CUDA stream.

## 5. Latency and speed model

The local `bench_rdma/perftest-summary.txt` measures each rail independently. Rail 1 reports 2.96 µs one way at 4,608 bytes and 6.24 µs at 36,864 bytes. Rail 2 reports 2.99 and 6.26 µs at the same sizes. Both reach about 109 Gbit/s each with larger messages. `bench_rdma/uma_allreduce_bench.cu:304–381` registers mapped host memory and verifies both ranks' arithmetic, but its timed loop uses one rail and synchronizes the device after both producer and reduction kernels. The stored `uma-summary.csv` is single-rail. It records directly measured end-to-end 96-op times, which include skew and tails that are hidden by multiplying individual-operation medians.

The graph estimate is `max(producer arrival across ranks) + GPU publish/proxy poll + dual post + max(rail 1, rail 2 transit) + CQ/ready handoff + GPU wait/reduce` relative to entering the operation. Symmetric simultaneous sends price one transit on the critical path, plus completion/ready and skew. Subtract the predecessor's arrival time when measuring isolated communication on aligned ranks. At TP=2 the slower rail's one-way time at half payload is the network anchor. These are planning ranges for aligned ranks, with 2.5–7.7 µs budgeted across posting, polling, scheduling and GPU work depending on width. Only the transit values in the measured size range come from perftest. The graph column excludes the head.

| 1 | 4,608 / 2,304 | ~2.7–3.1 µs, extrapolated | 16.801 | 1.982 | 5.5–9 | 0.528–0.864 ms |
| 4 | 18,432 / 9,216 | 3.67 µs | 18.160 | 1.905 | 6.5–10 | 0.624–0.960 ms |

| 16 | 73,728 / 36,864 | 6.26 µs | 23.552 | 2.490 | 9–14 | 0.864–1.344 ms |

For throughput-sized payloads, two measured 109 Gbit/s rails imply a best case of 218 Gbit/s (27.25 GB/s) per direction if the NIC, host interface and UMA fabric sustain both concurrently. One BF16 2,048-token prefill chunk sends 9,437,184 bytes per rank per SUM, about 33.2 ms wire-only for 96 exchanges at that aggregate rate. Treat dual-rail throughput, asymmetric rank skew and p95/p99 tails as separate M1/M3 measurements. Small-message startup dominates plain decode. FP32 hidden SUMs double the stripe bytes, and ordered expert exchanges, full logits, and Tree-16 scheduling need their own measurements.

The same checkout's `results/gb10-baseline.3MJbE9se/synthetic-{2048,32768,131072}.log` report 55.7–56.0 token/s with `--dense-fp8 --kv-fp8` and greedy decode. At 56 token/s, `T1=17.86 ms`. With shardable fraction `f=0.80–0.90`, `T2 ≈ T1*(1-f/2) + 0.528–0.864 ms + ~0.006–0.009 ms` for the hidden collectives and greedy head. That gives approximately **10.36–11.59 ms, 86–97 token/s (1.54–1.72×)**. This assumes roughly linear improvement for the sharded portion and no material kernel-split or tail cost beyond the estimate. For comparison, the existing naive M=1 communication median with the same compute assumption would give about 79–85 token/s (1.41–1.51×). W2 underfill, graph-kernel overhead, differing context lengths and a required wider precision path can lower the gain. At larger M, estimate spec token/s using measured width distribution and `emitted_tokens / (draft + target verify + acceptance + rollback + control)`. The 5–9 µs proposal transfer is per round, and the width-M target spends one set of 96 exchanges per round. A fixed speedup for DSpark or Tree-16 would need measured acceptance and candidate path lengths.

## 6. Implementation and verification milestones

### M1 · Graph-captured transport on two Spark ranks

Build a standalone transport target and the environment/bootstrap, without model loading. Capture 96 chained SUMs once per width and replay, with changing per-op and per-replay data that make stale slots and wrong rail halves fail immediately. Implement host proxy, GPU signal and finish kernels, mapped visibility checks, slot retirement and abort path. Verify all elements on both ranks against explicit BF16 operands added and rounded once. Exercise widths 1/4/8/16 and FP32, candidate gather and token broadcast smoke cases. Test one rail, both rails, rail completion order reversal, rank delay, repeated slot reuse, stale tag, absent peer, and teardown after failure. Include a cache-hot visibility test against previously accessed receive lines. Report graph wall-time p50/p95/p99 and per-op latency by width plus CPU core consumption and simultaneous per-rail byte counters. Stamp GPU publish/ready and host CQ events without comparing unsynchronized node clocks. Require zero stale/partial payloads or deadlocks across at least 10,000 96-op replays per width, zero per-op CUDA synchronization, and p50 for dual-rail M=1 below 0.9 ms for the 96-op chain before using the projected speedup as a target. Compare to the same-run single-rail control and record tail distributions.

### M2 · One-GPU two-rank layer simulation

Implement `TpLayout`, local loader views, head-range and expert slices, and the local `attn`/GEMV/MoE methods before coupling them to RoCE. On one GPU, execute two rank layouts with independent state and deterministic device exchanges. Cover sliding layer 0, a sliding loop visit with messages, a full loop visit with messages, and an MXFP8 visit (include full layer 23 and a sliding MXFP8 layer). Exercise passes 0–2, BF16 and FP8 dense, BF16/E4M3 full KV, active and zero ablation, widths 1/2/4/8, and ring wrap. Test shards at 4 and 8 in the packing harness, including whole-block MXFP8 boundaries and NVFP4 padding. Include selected expert ID extremes, uneven reused routes, every chunk tail, ties and a one-token start.

Require bit equality for packed checkpoint codes/scales and factors, reconstructed weights, unsharded-equivalent head-local projection/attention when fed identical operands and executed in the same arithmetic order, KV and K/V conv state, logits for fixed identical final hidden, and exact transport on the same TP operands. Compare gathered local W13 activations, both epilogues and all history/rollback buffers against the unchanged full-width arithmetic oracle. Build a bit-exact sharded-layer reference by reassembling heads and W13 activations and using the legacy dot/epilogue ordering in the simulated run. For production mode, compare against a deterministic TP reference implementing the same partials and operation ordering, then measure BF16 hidden vs FP32 hidden vs FP32 expert-ordered drift against legacy TP=1. Feed identical prior state into isolated comparisons and separately test divergence across visits. Capture and compare per-stage values around both exchanges, local KV, replicated histories, residual taps, router slots, and head margins. BF16 hidden reduction cannot promise bit parity with the old full-width attention or MoE dot.

### M3 · Full plain TP=2 on rank0 and rank1

Initialize both ranks from one pinned model/config. Run both the production chunked prefill and width-1 graph. Use rank-0 request admission, shared input schedule and collective sites. Check graph capture and eager fallback, prompt append, full/sliding caches, layer-6 restarts, prefix parking and resume. Rank 0 collects full logits for the validator in vocabulary order without using that path for the greedy speed run. Run `ingine-validate` distribution parity on the original, ablated where available, and both full-KV dtypes. Compare forced replay against a matched single-Spark native run with identical precision, chunking, flags and local kernel revisions. For the stock golden check retain the existing mean KL ≤0.01, max KL ≤0.25, and top-1 ≥0.95 gates. Add a matched-native TP comparison with the same hard KL/top-1 ceilings and report modes separately, along with logit margins and the first divergent visit. Require identical greedy tokens to matched native when the TP=1 top-1 margin exceeds twice the largest measured logit error on that row, and trace close calls. Include 2K, 32K and 128K benchmark prefixes and the first ring wrap. The stored single-Spark `orig_kv16` logit check passed at mean KL 0.003028, max 0.1466 and top-1 0.970. Its free-running long golden generated only 13/33 matching tokens in both plain and spec, so record that control and compare free generation directly with the matched native baseline.

Benchmark selected precision mode at the same contexts and report tok/s, TTFT, p95/p99, rank skew, local math time, exposed communication, memory, and collective count. If the fast BF16 variant misses the agreed parity criteria, isolate the first broken semantic boundary and use the passing precision mode for the performance result.

### M4 · DSpark linear verify, then Tree-16

Bring up rank-0 drafter ownership and the 32-byte proposal prefix for the existing 2/4/8 conditional graph. Check same-width/position entry, global head winners, accepted count, next anchor, tap commits, and rollback that restores overwritten sliding rows, per-visit conv history and live full-cache extent. Compare rollback to fresh replay of only the chosen prefix. Test every acceptance width and rejected-prefix length, token budget/EOS inside an accepted block, forced replay, and prefix restore. For sampled accept, use the full-logit/root path first and check fixed-seed decisions on shared logits plus the resulting distribution. Report tokens/verify, width distribution, control overhead, draft time, verifier and accept time, and generated token/s.

The audited native source implements linear DSpark and has no Tree-16 verifier. Add Tree-16 as an explicit second integration. Rank 0 broadcasts a fixed-capacity descriptor for up to 16 candidate rows, with token IDs, parent indices, depth/position and validity. This needs more than the linear 32-byte header. Both ranks use the same tree and batch shape. A candidate may read committed cache, its own ancestors and its newly processed row, with position-relative attention offsets derived from path depth. Its K/V, K/V convolution and post-write convolution need branch-local scratch for new rows. Each conv consumes its three preceding values along the chosen path. Sibling candidates may share a logical position and must not write one persistent ring slot. Compact the selected path into the main caches/history and advance both ranks by the same committed length. Keep one 96-exchange schedule for a tree batch if its rows are processed together. Validate each node against independently replaying its prefix and verify that rejected branches leave no persistent state. The initial tree acceptance can be greedy with deterministic global ties. Sampled trees need a defined branching proposal distribution and a matching acceptance algorithm. The linear `p/q` kernel alone does not provide that contract.
